**Neural-network investigation and proposal — 2026-09-18**

Planning only. No models were trained, features extracted, labels changed, or production assets modified. This investigation reads the implementation, prior studies, NAS metadata, and primary model/runtime documentation. Proposed architectures, budgets, and acceptance thresholds below are hypotheses for a future preregistered run, not measured results.

**Recommendation:** pursue a small temporal network plus a task-adapted visual representation. Run a cheap existing-feature control first, because it separates a classifier-capacity problem from information lost during feature extraction. In parallel, establish a desktop DINO-based reference that can also teach the mobile model. Invest new labeling effort primarily in end-of-play evidence and anonymous team-side state; defer extensive ball tracking until a small, independently evaluated pilot succeeds.

| Version | Labels | Inference | Proposed model | Main question |
| --- | --- | --- | --- | --- |
| 1. Existing labels, phone/browser | Audited existing exact labels; separately masked auxiliary labels | Fully on device | Tiny temporal convolutional network (TCN), then a compact visual encoder | Can learned interactions and spatial/temporal features improve cuts within the device budget? |
| 2. Richer labels, phone/browser | Version 1 plus targeted transition, court, and team-state annotations | Fully on device | Same compact backbone with additional supervised outputs; selective small perception modules only if justified | Can teaching the missing distinctions improve generalization more than adding model capacity? |
| 3. Desktop GPU | Same evaluation labels; optional richer annotations | Local RTX 3080 | Frozen DINO regional features + temporal head, then a motion-pretrained video branch and selective boundary refinement | What additional accuracy is attainable when richer perception is affordable? |

The versions share labels, folds, interval semantics, and evaluation. Desktop inference does not require cloud processing. It can also produce training targets for version 1 or 2, but mobile deployment must run entirely from inputs computed on the phone/browser.

**1. What exists today, and what the plateau does and does not establish**

The deployed core unions two independently decoded three-head logistic bundles. Each predicts live play, serve contact, and dead state. The current extractor uses **104 base signals at 4 Hz and 192×108**, expanded at five offsets from −2 to +2 seconds into **520 inputs**. Older research documents describe 90/450; those numbers are not the current deployed schema. The signals already include spatial brightness/difference/flow grids, camera compensation, formation and stand-down proxies, and audio transients/noise-normalized bands. Many signals are ranked within a recording. The learned classifier remains additive over these engineered inputs. See [feature schema](../../prod/src/lib/on-device/feature-schema.ts), [runtime](../../prod/src/lib/on-device/model.ts), and [Python extractor](../../analysis/features.py).

Serving-side classification is a separate near/far logistic model over 237 phase/flight-motion features around a proposed serve. The side-switch model uses 34 palette, production-state, and candidate features. Its candidates come from rally gaps and internal dead-state peaks. Optional suppression remains subject to the approved agreement protection policy and is disabled by default. These are distinct tasks: better serving-side classification cannot recover a missing serve, and a better switch classifier cannot select a switch absent from its candidate set. See [serving-side runtime](../../prod/src/lib/on-device/serving-side-model.ts), [side-switch runtime](../../prod/src/lib/on-device/side-switch-model.ts), and [suppression runtime](../../prod/src/lib/on-device/suppression-model.ts).

There is already relevant neural evidence:

| DINOv2 regional features + audiovisual TCN + boundary heads | Event F1 0.5544 versus 0.4640 for an audiovisual TCN; time IoU 0.5179 versus 0.4543, on 8 recordings / 4 source groups / 306 rallies | Learned visual information has helped before. This was not a comparison against today's production ensemble under today's metric. |

Sources: [executed DINO study](./dinov2-temporal-execution-2026-08-13.md), [MobileNet and feature ledger](./feature-experiment-order-execution-2026-08-12.md), [multistate diagnostics](./multistate-followup-execution-2026-08-12.md), and [T20 outcome](./side-switch-t20-compact-medoid-disagreement-plan-2026-08-25.md).

The historical neural runner still selects using `0.55*eventF1 + 0.30*timeIoU + 0.15*liveTimeRecall`. It must be changed to the current ranking contract before reuse. Its 90-signal input also requires an explicit schema migration. No final DINO checkpoint was published by that study. Its positive result supports a new investigation; it is not a deployment-ready winner. See [study implementation](../../analysis/semantic_temporal_study.py).

My assessment is that a neural network could help, particularly through richer visual evidence and temporal interactions. The record does **not** establish that linear model capacity alone caused the plateau. Data diversity, noisy/missing supervision, discarded spatial information, candidate coverage, and decoding all remain plausible limits.

**3. Version 1: existing labels, designed for phone/browser inference**

Start with three controlled capacity comparisons using identical current features: a refitted linear head, a small MLP over the existing 520-input context, and a TCN over the 104-channel sequence. Keep the shipped ensemble as a descriptive product/regression reference, with its training exposure disclosed. For generalization claims also refit a replica of the production architecture/ensemble entirely within each outer fitting fold; shipped weights may already have seen the held group. This distinguishes nonlinear interactions from longer temporal context and from a simple benefit of new training data.

The first TCN would use a 64-channel projection and five residual blocks, each with **one** depthwise temporal convolution and pointwise channel mixing; kernel size 5 and dilations 1, 2, 4, 8, 16 give a 125-tick convolutional field, approximately 31 seconds at 4 Hz. Target **30,000–250,000 parameters** across the basic and fused-input variants, with live, serve-contact, and end-of-play outputs. These are design budgets, not benchmark results. Dilated temporal convolution is a well-established action-segmentation approach; published results in other activities do not guarantee volleyball gains. [MS-TCN paper](https://arxiv.org/abs/1903.01945).

This is a smaller, deployment-oriented variant of the existing research TCN, not a claim that TCNs are new to the repo. Existing `GroupNorm` operates across time and makes output chunk-dependent. For the new model use fixed inference normalization, such as batch normalization folded into convolutions, and verify complete-sequence versus overlapped-chunk equivalence. Avoid a hidden dependence on chunk length. The existing [neural implementation](../../analysis/semantic_temporal_model.py) is useful scaffolding, not an unchanged export target.

Training targets need no new labels: a reviewed `[serve, dead)` interval gives live-state supervision and two separate boundary targets. Start with narrow soft boundary pulses on the actual sampled timeline and a masked weighted BCE loss `live + 0.5*serve + 0.5*end`. Select pulse width and class weights only inside development folds. Do not invent five-second setup labels or equate a short rally with a verified service fault. End-event prediction is distinct from the broad dead-state complement. It cannot be substituted directly into the existing sustained-dead decoder: first compare live-only decoding across models, then compare a common event-boundary decoder using matched event-head targets for linear/MLP/TCN controls. Keep the production three-head decoder as its own faithful baseline.

After the capacity comparison, introduce new feature families individually:

| Proposed feature | What changes from today | Why it may help | On-device constraint |
| --- | --- | --- | --- |
| Small spatial motion tensor | Preserve signed camera-compensated flow/difference/occupancy on a somewhat finer grid, rather than adding more copies of existing 3×3 summaries | Separates coordinated court play from one walking player or adjacent-court motion | Reuse sampled frames and existing flow; compare extra reduction cost |
| Learned regional visual embedding | MobileNetV3-Small-class encoder; retain spatial pools for full/near/far areas, project to roughly 64–128 features | Learns posture, formations, retrieval, and stand-down appearance that scalar motion loses | Start one full-frame feature map at 2 Hz; use 4 Hz AV for boundaries; benchmark 160/192/224 inputs |
| Short spectral audio tensor | Small log-mel patch rather than only scalar transient/band reductions | Could distinguish contact, whistle, and celebration in context | Add only after visual ablation; missing-audio mask and modality dropout are essential |
| Availability and quality | Explicit missing/cropped/blur/occlusion flags and elapsed-time channels | Lets the model discount unreliable evidence | All flags must be computed from inference-visible inputs |

The compact image encoder should start with pretrained weights, train the temporal/projection layers first, and then unfreeze a small final stage with a lower learning rate. Compare direct supervised training against task-specific teacher distillation. Preserve temporal order and spatial correspondence; do not repeat the failed random-projected MobileNetV2 experiment. TorchVision documents MobileNetV3-Small at about 2.54M parameters and 0.06 GFLOPs under its published reference configuration; this is a scale reference, not a latency claim for our crops/runtime. [Official model documentation](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.mobilenet_v3_small.html).

The stronger teacher can provide live/serve/end probabilities and regional representations from development training groups. Train the student on ground truth plus a modest distillation term; compare against ground-truth-only training. Each outer/inner fold must exclude its evaluation groups from teacher fitting, pseudo-label generation used for fitting, calibration, and adaptation. Never let teacher confidence override known gold errors. The student's deployment path receives only its own small encoder, AV features, and masks.

Initial model-size targets are under 1 MB of weights for the temporal-only model and under 5 MB INT8 or 10 MB FP16 for the compact visual model. Runtime libraries and activation memory are separate costs. Start with ONNX Runtime Web WASM as the portable execution target and evaluate WebGPU where available; establish Android/iOS parity with ONNX Runtime Mobile before deciding whether a native-specific runtime is worth a second conversion path. Both mobile and web runtimes exist, but accelerator operator support and performance vary. [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/), [mobile deployment](https://onnxruntime.ai/docs/tutorials/mobile/).

Use fixed-shape chunks, ordinary convolution/activation/pooling/linear operations, bounded image buffers, worker execution, cancellation, and versioned resumable caches. Train and infer with the same aspect-ratio/ROI handling; do not blindly use a center crop that removes service zones. Per-recording percentile normalization currently implies whole-recording statistics; preserve the existing two-pass/cache contract initially. A causal/live-streaming redesign is a separate task.

Quantize only after FP32 parity. Calibrate from training groups, compare INT8 CPU and FP16 accelerated paths, and rerun interval metrics after conversion. Smaller weights do not guarantee faster execution; unsupported operators or CPU/GPU transfers can dominate. Budget the runtime download as well as model weights. [ONNX quantization guidance](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html).

**4. Train and judge version 1 in a way that answers the actual question**

Use WSL2 Ubuntu 24.04 on this machine. The observed GPU is **RTX 3080, 10,240 MiB**, driver 576.80. Store hot caches and the experiment environment on WSL's local filesystem; retain source videos and immutable results on the NAS. Existing DINO work already qualified this 10 GB device. No setup or extraction is performed as part of this proposal.

Freeze a manifest containing video/label hashes, source groups, consent, annotation tier, ignored ranges, and prior exposure. Use nested source-group-held-out development: the inner groups select checkpoints/decoder settings, the outer group measures transfer. Balance sampling by source group/recording as well as live/dead and rare-event strata. Frame count is not sample independence. Restrict learned scalers, PCA if used, class weights, quantization calibration, and hard-negative mining to the fitting partition.

A concrete initial training recipe is AdamW, temporal-head learning rate around `1e-3`, later encoder unfreezing around `1e-5`, weight decay around `1e-4`, dropout around 0.1, three fixed seeds, and a 30-epoch cap with early stopping inside inner folds. These are starting settings, not a large search grid. Begin with batches of 8–16 cached feature sequences. For encoder fine-tuning, start with short differentiable windows of 8–16 frames and one window per microbatch, measure VRAM, then recache embeddings for long-context temporal training. A 64-second chunk at 2 Hz contains 128 images: gradient accumulation alone does not make that entire activation graph fit. Checkpointed frame microbatches are a later alternative. Use mixed precision and reserve at least 1 GB of the card rather than assuming all nominal memory is free.

Use approximately 64-second feature chunks, score the central 32 seconds, and provide enough halo for the specified receptive field. Mask synthetic padding and ignored time; do not smooth targets or propagate temporal state across camera cuts/unknown gaps. Oversample real short rallies and hard negatives without changing evaluation prevalence. Train on exact timestamps, not presumed uniform source-frame cadence. Apply consistent spatial/color augmentation across an entire clip; aggressive time warps can destroy contact labels. Audio dropout, compression/brightness variation, and modest crop perturbations are useful robustness hypotheses. Near/far is camera depth: a horizontal flip does not swap those labels.

Freeze the following small experiment ladder rather than trying every backbone/head combination:

| Step | Comparison | Interpretation |
| --- | --- | --- |
| A | Shipped ensemble as descriptive reference; fold-refitted production replica and linear control | Establish exposure-safe architecture comparisons and the value of new training labels |
| B | Linear versus small MLP versus compact TCN, same 104 base signals | Test nonlinear interactions and temporal context |
| C | TCN versus TCN + one spatial-motion family | Test retained spatial information at low cost |
| D | Best compact control versus task-adapted visual student | Test learned perception; include a linear readout of the same frozen embeddings to separate representation from head effects |
| E | Same visual student with versus without teacher supervision | Test whether desktop-quality supervision transfers |
| F | Optional audio tensor, only if residual error review supports it | Test acoustic information rather than adding channels indiscriminately |

Train with dense losses; **select all checkpoints, architectures, seeds/ensembles, and decoders using the declared product metric**. Keep one matched decoder configuration for diagnostic attribution, then give controls and candidates the same inner-fold decoder-tuning budget. Do not select the best seed after inspecting outer results. A larger gain from the teacher than the student means compression/perception remains the obstacle. No gain from B but a gain from D supports an information bottleneck; a strong training score with poor held-group performance points toward data diversity or shortcuts.

Predeclare target export padding **(2 s, 2 s)** and rank by pooled `F1_padP_coreR`, following the [canonical metric](../model-ranking-metric.md). For each candidate report all four symmetric cases `(0,0)`, `(1,1)`, `(2,2)`, `(3,3)`, including pooled `P_pad`, pooled `R_core`, `F1_padP_coreR`, padded model duration, padded human duration, and their difference. Clip and union intervals, join positive gaps **strictly below 3 seconds** in both padded unions, exclude identical ignored ranges from every relevant union, and never rejoin across ignored spans. Pool duration numerators/denominators before F1; do not average per-video F1.

Proposed feasibility gate: at least **+0.02 absolute development `F1_padP_coreR`** at 2 s, consistent across seeds and a majority of independent groups, with pooled `R_core` no more than 0.005 below the reference. Report event F1, short/ace/fault recall, complete/partial rally losses, start/end errors, export seconds, and per-environment/quality slices. For a production replacement, additionally require no new non-exempt complete rally losses and no material partial-coverage regression on the declared safety suite. These are proposed thresholds to freeze before execution, not established product guarantees. Use source-group paired uncertainty intervals; four groups alone cannot yield a strong generalization claim.

Measure the **full** device pipeline on Android, iPhone/iPad, and browsers with and without GPU acceleration: cold/warm wall time per source minute, decode/resize/feature/inference times, peak memory, model/runtime download, and thermal behavior on a full recording. A provisional mobile gate is at most 25% more total analysis time than the current path on each required device, with added peak working memory under 150 MB for the visual branch and 32 MB for temporal-only inference. Calibrate these engineering budgets on representative devices before model selection; no phone benchmark is claimed here.

One existing Pixel specialist benchmark took 463.954 seconds on a 1,105.817-second source, of which 428.822 seconds was shared decoding. Sparse neural calls do not automatically produce a cheap pipeline: GOP preroll and extra decode passes matter. Share requests, decode forward within dense segments, and retain the measured gap-aware seeking strategy across long gaps rather than forcing a full sequential pass for sparse specialists. See [measured Android pipeline](./android-team-switch-production-port-2026-08-23.md).

Keep the protected test closed during iteration. Existing repeatedly examined scopes are regression evidence, not a fresh final test. Reserve new, genuinely uninspected source matches with diverse courts, devices, formats, and short-event content for one locked final evaluation. The expanded corpus must not silently absorb relatives of that holdout.

**5. Version 2: labels that would unlock better compact models**

New labels do not make a feature mathematically computable; they make its intended meaning learnable and independently testable. Prioritize the supervision below instead of labeling every possible volleyball event.

| Priority / proposed labels | Features and neural objective unlocked | Why this matches current failures | Suggested first annotation batch |
| --- | --- | --- | --- |
| 1. Reaction, terminal cue, collective stand-down, boundary confidence/observability | Local posture/motion/audio embeddings with reaction/end/stand-down heads; confidence-weighted or interval-censored boundary losses | The terminal event and subsequent stopping motion occur at different times. Current summaries can confuse retrieval with live play. | About 15–25 stratified rallies per development recording: short/fault, ordinary, hard endpoints; independently double-review a subset |
| 2. Short phase spans: ready/setup, live, retrieval/walking, celebration/huddle, unknown | Compact multi-head temporal state model; explicit hard-negative subclass supervision | Teaches distinctions that binary dead time collapses, while preserving immediate serve-to-dead cases | Roughly 3–5 difficult negatives plus 3–5 random dead controls per recording, with reviewed span coverage |
| 3. Anonymous team-side state in stable windows, plus switch start/end and uncertainty | Same-team versus swapped-team embedding loss; near/far set representations and a small temporal consistency model | Directly supervises team correspondence rather than asking noisy color differences to discover it from a few switch events | Stable pre/post windows around every development switch, and 2–3 matched no-switch/huddle/camera-motion pairs per switch |
| 4. Court corners/net/service-zone anchors, updated after camera movement | Court-relative feature-map pooling, player occupancy and service-zone motion; optionally a tiny court estimator later | Reduces background shortcuts and handles near/far scale differences | One clear frame per stable camera segment; omit genuinely invisible anchors |
| 5. Sparse anonymous player boxes/footpoints, short tracklets, coarse action state | Small player/pose representation, speed/spacing/reaction synchrony, team assignment | Separates coordinated multi-player action from isolated walking and foreground crossings | Extend the existing five-rallies-per-recording tracklet pilot; cover both boundary windows and both sides |
| 6. Ball centers/visibility and short trajectories, explicit contacts and terminal events | Volleyball-specific temporal heatmaps, velocity/acceleration, net crossing and player-ball interaction | Gives direct contact/terminal evidence when the ball is resolvable | A bounded 100–200 difficult/ordinary clips, several frames each, with independent held-source clips; audit existing ball annotations first |
| 7. Verified point outcome, replay/let/penalty, missing-point and set-reset markers | Score-sequence consistency and uncertainty-aware winner tracking | Serving-side and switch mistakes compound into score errors; a side label alone is not a verified point outcome | Only if score accuracy becomes a primary acceptance objective |

The first two priorities mostly fit existing schema fields and the proposed compact encoder. Label the physical dead-ball moment separately from delayed collective stand-down. Use `unobservable` or a reviewed uncertainty interval rather than guessing. A partly observed start/end does not authorize treating surrounding unlabeled time as dead.

For side switching, anonymous team A/B names are arbitrary **within a recording**, not player identities across matches. Use permutation-invariant same-versus-swapped supervision. Exhaustive switch markers can derive relative parity only within uninterrupted, fully reviewed segments; absolute near/far team assignment needs an anchor. Reset at cuts, unknown switches, or set breaks. Stable state anchors provide a check against incomplete marker histories. Add periodic low-rate state evidence to recover switches absent from production gap candidates; evaluate this candidate expansion separately from the classifier.

Train phase and uncertainty heads with masked losses; leave unannotated fields unknown. Do not force a rigid setup → serve → long rally sequence, because faults and aces need an immediate terminal transition. Use phase consistency as soft evidence. For side state, a small set-pooling or shared pairwise network over near/far team embeddings is a better structural match than a large general-purpose Transformer trained on approximately dozens of switch events.

Ball-dependent work ranks lower because the prior generic detector failed its development gate, and increasing model capacity cannot recover a ball lost during downsampling. Ball absence is also not dead-play evidence when the ball is occluded or off-camera. Higher-resolution temporal crops may be affordable selectively on mobile and broadly on desktop, but any deployed crop/detector must have its own held-source localization/visibility evaluation. Existing sparse ball-presence review is useful pilot material, not a ready-made dense trajectory dataset. See [ball pilot](./minimum-ball-presence-pilot-2026-08-11.md).

Serving side can first reuse its existing reviewed near/far decisions to train a small shared near/far clip encoder with a calibrated review option. Report accuracy/balanced accuracy and coverage at abstention thresholds, but also measure end-to-end serving-side correctness over independently reviewed true serves. A candidate-conditioned score can hide missed serves. Keep this specialist separate initially; share a visual encoder only after verifying that multi-task training does not hurt rally coverage.

For switch detection, report candidate recall separately from one-to-one event precision/recall/F1 under the existing strict and ±4-second matching contracts, false switches per recording/hour, and persistent team-side errors after a false or missed switch. Use recording/source-held evaluation and independently reviewed switch completeness. `F1_padP_coreR` ranks rally exports; it is not an appropriate substitute for these specialist metrics.

For annotation efficiency, mix difficult model-disagreement examples with randomly sampled controls and new courts/cameras. Add a small boundary double-annotation study to measure the label error floor. Additional independent matches are likely more valuable than densely annotating another thousand highly correlated frames from an already overused set. Record annotator, review completeness, uncertainty, and assisted-label provenance; freeze revisions before training.

**6. Version 3: desktop inference on the local RTX 3080**

Desktop compute changes the perception budget substantially, but not the quantity of independent supervision. The first desktop experiment should recover and extend the **existing successful DINO design**, not start with a generative video model.

| Desktop stage | Concrete design | What it adds beyond mobile |
| --- | --- | --- |
| D1. Re-established reference | Frozen DINOv2-S/14 at 336 px, full/regional pooled tokens at 4 Hz, current AV channels, live/serve/end temporal head | Richer pretrained appearance representation at every analysis tick; directly builds on executed code |
| D2. Genuine motion representation | One frozen motion-pretrained encoder, initially VideoMAE ViT-S, on bounded 16-frame clips; fuse its output with D1/AV in a temporal head | Sees coordinated action within a clip rather than inferring all motion from independent images or optical-flow summaries |
| D3. Selective boundary refinement | Around predicted or uncertain contacts/ends, inspect native-source crops at 8–16 Hz over roughly ±2 seconds; predict a refined boundary/visibility | Finer timing and more resolvable hands/ball/player motion without processing an entire recording at high resolution |
| D4. Specialist perception, after label gates | Learned near/far team/player embeddings over stable pre/post windows; optional qualified ball track branch | More reliable team correspondence, ball interaction, and occlusion reasoning |

DINOv2 provides reusable image/patch representations; VideoMAE publishes small video models and pretrained checkpoints. Their published benchmark results are not volleyball accuracy estimates. Use the official implementations/checkpoints, pin exact revisions and verify their artifact terms during execution. [DINOv2 repository](https://github.com/facebookresearch/dinov2), [VideoMAE model zoo](https://github.com/MCG-NJU/VideoMAE/blob/main/MODEL_ZOO.md).

For D2, choose clip sampling according to the pinned checkpoint's expected temporal stride, map features to true video timestamps, and compare motion-only versus image+motion fusion. Start a single clip/view per location. Do not assume a sports-action classifier understands serve contact or dead-ball timing without a supervised temporal head. Adding a temporal-shift module to a compact 2D encoder is a possible later student alternative if D2 shows useful motion information; it should be a separate experiment, since nominally cheap shifts still incur memory movement in real runtimes. [TSM paper](https://openaccess.thecvf.com/content_ICCV_2019/html/Lin_TSM_Temporal_Shift_Module_for_Efficient_Video_Understanding_ICCV_2019_paper.html).

Use a continuous coarse path over the whole recording. A refinement stage limited to existing production proposals cannot recover entirely missed rallies; include independently triggered high-uncertainty/serve-evidence regions, measure proposal coverage, and retain the coarse model's ability to discover events. Audit timestamp precision and annotation uncertainty before claiming finer localization: the labeling guide's 0.25-second accuracy target is neither a timestamp quantization rule nor evidence that every boundary meets it. Use independently checked contact/terminal labels to assess sub-frame-grid improvements.

Training can cache frozen DINO/video features and fit the temporal fusion head comfortably before trying any encoder fine-tuning. Refit and save a proper teacher checkpoint under the current label/metric contract. Only unfreeze upper encoder layers if grouped validation shows head saturation and the 10 GB memory probe passes. Use mixed precision, small batches, and gradient accumulation. Full encoder training from scratch, large video-language models, and end-to-end full-match attention are poor initial uses of this dataset and hardware.

The earlier 336-pixel DINO probe measured roughly 94 frames/s on this same class of 10 GB card, but only over 32 frames. It excludes a complete NAS/decode/multi-crop/fusion pipeline, so it cannot establish full-match runtime. Measure real sequential NVDEC/CPU decode, source reads, preprocessing, inference, and caching separately. Batch frames/clips, reuse decoded frames between branches, and bound VRAM with a measured safety reserve. A proposed desktop acceptance target is at least real-time full-video processing and no memory offload; report throughput even if an accuracy-positive prototype misses that target.

A desktop user could run a local Python/native analysis worker and open the resulting cuts in the existing UI. GPU use would occur in that local worker; browser WebGPU alone is a different deployment path with its own operator and memory limits. Keep the same analysis output contract and source-time provenance so both products remain comparable.

Evaluate D1, D2, and D3 as separate additions using the same folds and 2-second ranking metric. Desktop earns a separate product option only if its additional accuracy or lower editing burden justifies its runtime and model-download cost. A high-quality desktop model that cannot be compressed is still useful under this third version; it should not be presented as successful phone inference.

**7. Proposed execution order and deliverables**

1. Reconcile eligible existing labels and source-group lineage, freeze annotation tiers and a fresh final holdout, and replace the historical neural runner's selection objective. Publish the manifest/counts and a documented current-ensemble baseline before any new model comparison.
2. Qualify portable operations and memory on phones/browser with a small synthetic model, then run A/B on cached current features. Run desktop D1 with the same data contract. These establish cheap-model and richer-representation references.
3. Run the mobile spatial/visual student comparisons, followed by distillation only if the teacher provides a useful gain. Measure actual end-to-end devices early; stop expanding an encoder that fails the budget.
4. Run desktop D2, and D3 only if boundary error remains important. Add the first transition-label pilot concurrently; keep new-label comparisons paired on the same recording scope.
5. Extend to team-state labels and specialist networks after rally results are understood. Defer the ball-label investment until its small pilot meets localization/transfer gates.
6. Freeze the selected configuration, test conversions and runtime parity, then open the new held-source evaluation once. Keep model changes reviewable; no production promotion is implied by this plan.

Each completed experiment should produce model/config hashes, label/video lineage, per-head masks and losses, all held-group predictions, three-seed results, the complete padding table, failure slices, runtime/memory/download measurements, and a short decision explaining whether the gain came from capacity, representation, supervision, or decoding. Include a compact review pack of new misses and removed false positives, not just one headline F1.

The highest-value initial package is therefore **current-feature MLP/TCN controls + a refreshed desktop DINO teacher/reference + one compact visual student**. It tests the plateau hypothesis with existing labels, gives a concrete phone/browser path, and establishes whether desktop-only inference can deliver enough additional quality to justify its own version.
